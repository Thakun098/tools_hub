# แผนรองรับไฟล์สื่อขนาดใหญ่

## เป้าหมาย

ทำให้ Free SRT รองรับวิดีโอ โดยเฉพาะ MP4 ขนาดหลาย GB บน Portable Windows ได้อย่างปลอดภัยและเข้าใจง่าย โดยหลีกเลี่ยงการคัดลอกไฟล์ต้นฉบับผ่าน browser/Flask เมื่อผู้ใช้ทำงานบนเครื่องเดียวกัน

ผลลัพธ์ที่ต้องการคือ ผู้ใช้เลือกไฟล์จาก Windows โดยตรง แล้ว FFmpeg อ่านไฟล์ต้นฉบับตามตำแหน่งเดิมเพื่อสร้าง WAV ชั่วคราวสำหรับ whisper.cpp โปรแกรมจะไม่แก้ไขหรือลบไฟล์ต้นฉบับของผู้ใช้

## สถานะปัจจุบันและปัญหา

- Flask ยังไม่ได้กำหนด `MAX_CONTENT_LENGTH` จึงไม่มีเพดานอัปโหลดจากแอป
- การเลือกไฟล์หรือ drag-and-drop ใน browser ส่งไฟล์แบบ multipart ไปยัง Flask
- สำหรับไฟล์ใหญ่ Werkzeug อาจใช้ Windows Temp ก่อน แล้วแอปบันทึกสำเนาเข้า `uploads/` อีกครั้ง
- MP4 ขนาด 5 GB จึงอาจต้องใช้พื้นที่ชั่วคราวราว 10 GB หรือมากกว่า แม้ตัวไฟล์จะไม่ได้ถูกโหลดทั้งก้อนเข้า RAM
- FFmpeg จะแปลงทุกอินพุตเป็น WAV 16 kHz mono PCM ก่อนส่งให้ whisper.cpp ตามสถาปัตยกรรมปัจจุบัน
- WAV มีขนาดประมาณ 115 MB ต่อชั่วโมงของเสียง; ความยาววิดีโอมีผลต่อขนาด WAV และเวลาถอดเสียงมากกว่าขนาด MP4 เพียงอย่างเดียว
- worker ปัจจุบันลบ `input_path` หลังจบงาน ดังนั้นต้องแยกชัดเจนว่าไฟล์ใดเป็นสำเนาที่แอปเป็นเจ้าของ และไฟล์ใดเป็นต้นฉบับของผู้ใช้

## ขอบเขตที่เสนอ

### 1. เลือกไฟล์จากเครื่องโดยตรง (Local File Picker)

เพิ่มปุ่มหลักในหน้าเริ่มงาน เช่น **เลือกไฟล์จากเครื่อง (แนะนำสำหรับไฟล์ใหญ่)**

- Portable EXE เปิด Windows file dialog จาก backend ผ่าน `tkinter` หรือ native dialog ที่บรรจุพร้อม PyInstaller
- รองรับนามสกุลสื่อที่ UI แสดงอยู่แล้ว เช่น `.mp4`, `.mov`, `.mkv`, `.avi`, `.webm`, `.mp3`, `.wav`, `.m4a`, `.aac`, `.flac`, `.ogg`
- Backend ส่งกลับเฉพาะ `selection_id`, ชื่อไฟล์ และขนาด ไม่ส่งพาธเต็มกลับหน้าเว็บ
- เมื่อเริ่มงาน หน้าเว็บส่ง `selection_id` แทนการแนบไฟล์ทั้งก้อน
- Backend เก็บ mapping ของ `selection_id` กับพาธจริงใน memory และกำหนดอายุสั้น ๆ เพื่อไม่ให้เรียกใช้ซ้ำโดยไม่ตั้งใจ
- ไม่รับ path จาก browser โดยตรง เพื่อไม่ให้ API หน้าเว็บเข้าถึงไฟล์ใดก็ได้บนเครื่อง

ข้อจำกัด: native file picker เหมาะกับ Portable EXE ที่ Flask และ browser ทำงานบนเครื่องเดียวกันเท่านั้น สำหรับ Docker หรือ server ที่อยู่คนละเครื่อง ต้องใช้ upload แบบเดิม

### 2. รักษาโหมด Upload เดิมไว้

คง file input และ drag-and-drop ไว้ เพื่อความเข้ากันได้กับการใช้งานเดิมและโหมด Docker/server

- ระบุใน UI ว่าเหมาะกับไฟล์เล็ก และจะมีการคัดลอกไฟล์เข้าโปรแกรม
- เมื่อเป็นไฟล์ใหญ่ ให้แนะนำปุ่มเลือกไฟล์จากเครื่องแทน
- ยกเลิก upload ยังคงใช้ `XMLHttpRequest.abort()` ได้ตามเดิม

### 3. แยกความเป็นเจ้าของไฟล์อย่างชัดเจน

ปรับข้อมูลของ job ให้ระบุว่า input เป็นของแอปหรือของผู้ใช้:

| แหล่งไฟล์ | ตัวอย่างพาธ | ลบหลังงานจบ |
| --- | --- | --- |
| Upload ผ่าน browser | `uploads/<task>_orig.mp4` | ลบ |
| เลือกจากเครื่อง | `D:\\Videos\\source.mp4` | ห้ามลบ |
| WAV ที่ FFmpeg สร้าง | `uploads/<task>.wav` | ลบ |
| SRT ที่ไม่สมบูรณ์ | `outputs/<task>.srt` | ลบเมื่อยกเลิก/ผิดพลาด |

ต้องให้ cleanup ทุกกรณี—สำเร็จ, ผิดพลาด, หรือยกเลิก—ยึดตาม ownership นี้เสมอ

### 4. วิเคราะห์ไฟล์และตรวจพื้นที่ก่อนเริ่มงาน

ใช้ `ffprobe.exe` ที่มากับ portable build เพื่อตรวจแบบ read-only ก่อนสร้างงาน:

- ไฟล์ยังอยู่และอ่านได้
- มี audio stream อย่างน้อยหนึ่งแทร็ก
- ระยะเวลาสื่อและข้อมูล stream พื้นฐาน
- ประมาณขนาด WAV ที่ต้องใช้
- พื้นที่ว่างในไดรฟ์ที่เก็บ `uploads/` และ `outputs/`

ตัวอย่างข้อความที่ UI ควรแสดง:

> วิดีโอยาว 3 ชั่วโมง จะสร้างไฟล์เสียงชั่วคราวประมาณ 346 MB แนะนำพื้นที่ว่างอย่างน้อย 1 GB ไฟล์ต้นฉบับจะไม่ถูกแก้ไขหรือลบ

หากพื้นที่ไม่พอหรือไม่มีเสียง ให้หยุดก่อนเริ่ม FFmpeg พร้อมข้อความภาษาไทยที่บอกทางแก้ได้

### 5. ควบคุมงานพร้อมกัน

เริ่มจากการอนุญาต transcription ทีละหนึ่งงานใน Portable mode

- ปิดปุ่มเริ่มงานใหม่ระหว่างทำงาน
- ยกเลิกงานเดิมได้
- ไม่เพิ่ม Redis, Celery หรือ persistent queue ในระยะนี้

เหตุผลคือการถอดเสียงไฟล์ยาวใช้ CPU, RAM และพื้นที่ดิสก์มาก การจำกัดหนึ่งงานทำให้พฤติกรรมคาดเดาได้สำหรับผู้ใช้กลุ่มเล็ก

## ลำดับการทำงาน

1. เพิ่มโครงสร้าง `local_selections` และ API สำหรับเปิด native file picker/เรียกใช้ selection อย่างปลอดภัย
2. ปรับ API เริ่ม transcription ให้รับได้ทั้ง upload และ `selection_id` พร้อมตรวจว่าระบุเพียงแบบเดียว
3. ปรับ worker และ cleanup ให้ใช้ flag ownership; เพิ่ม guard เพื่อไม่ลบไฟล์ต้นฉบับเด็ดขาด
4. เพิ่ม wrapper สำหรับ `ffprobe` และตรวจพื้นที่ว่างก่อนเริ่มงาน
5. ปรับ UI ให้มีสองทางเลือกพร้อมคำอธิบาย, แสดงผลวิเคราะห์ และเตือนกรณีไฟล์ใหญ่
6. ตรวจ PyInstaller ให้รวมส่วนของ native dialog และ `ffprobe.exe` โดยไม่บรรจุ binary ซ้ำ
7. เพิ่ม tests, ทดสอบ Portable build จริง, แล้วอัปเดตเอกสาร/release ZIP

## ไฟล์ที่คาดว่าจะกระทบ

- `app.py` — API, selection store, job ownership, preflight สื่อ/พื้นที่, FFprobe และ cleanup
- `templates/index.html` — ปุ่มเลือกไฟล์โดยตรง, สถานะไฟล์ และคำแนะนำ
- `static/app.js` — state ของ local selection, เรียก API, และ flow เริ่มงานสองแบบ
- `static/styles.css` — รูปแบบตัวเลือกไฟล์และกล่องคำเตือน
- `FreeSRT.spec` — ตรวจการบรรจุ dependency ของ native picker (ถ้าจำเป็น)
- `scratch/test_app_unit.py` — regression tests
- `README.md`, `PORTABLE_BUILD.md`, `update.log.md`, `AGENTS.md` — วิธีใช้, ข้อจำกัด, และ invariant ใหม่

## ความเสี่ยงและแนวทางลดความเสี่ยง

| ความเสี่ยง | วิธีจัดการ |
| --- | --- |
| ไฟล์ต้นฉบับถูกลบจาก cleanup | เพิ่ม ownership flag, test ทั้ง success/error/cancel และใช้ค่า default แบบปลอดภัยคือไม่ลบ |
| ผู้ใช้เลือกไฟล์แล้วไฟล์ถูกย้าย/ถอด drive ก่อนเริ่ม | ตรวจ `isfile` และความสามารถในการอ่านซ้ำก่อนสร้าง process พร้อมข้อความชัดเจน |
| file picker ไม่ทำงานใน Portable build | ทดสอบบน clean Windows และเพิ่ม hidden imports/data ที่ PyInstaller ต้องใช้ |
| การเรียก API อ้าง path อื่นโดยมิชอบ | ใช้ opaque, one-time, expiring `selection_id`; ห้ามรับ raw path จาก browser |
| พื้นที่ไม่พอระหว่างทำงาน | ตรวจพื้นที่ก่อนเริ่ม, เผื่อ margin และเก็บ error ของ FFmpeg ให้อ่านง่าย |
| 5 GB อยู่บน FAT32 | แจ้งว่าต้องใช้ NTFS หรือ exFAT เพราะ FAT32 เก็บไฟล์เดี่ยวเกิน 4 GB ไม่ได้ |
| งานหลายชุดทำให้ทรัพยากรหมด | จำกัดการถอดเสียงพร้อมกันหนึ่งงานใน Portable mode |

## เกณฑ์ยอมรับ

- เลือก MP4 ขนาดใหญ่ผ่าน native dialog แล้ว FFmpeg อ่านไฟล์ต้นฉบับโดยตรง โดยไม่มีสำเนา MP4 ใน `uploads/`
- ไฟล์ต้นฉบับไม่ถูกแก้ไขหรือลบ ไม่ว่างานจะสำเร็จ ล้มเหลว หรือถูกยกเลิก
- WAV และ SRT ชั่วคราวถูกลบตามกติกาปัจจุบัน
- ไฟล์ที่ไม่มี audio stream, ไฟล์ถูกย้าย, หรือพื้นที่ไม่พอ แสดง error ภาษาไทยก่อนเริ่มงาน
- Upload/drag-and-drop เดิมยังทำงานได้และลบสำเนาที่ `uploads/` หลังงานจบ
- API ไม่เผยพาธเต็มของผู้ใช้ และไม่ยอมรับ raw path จาก browser
- การยกเลิกยังทำงานได้ทั้งระหว่าง FFmpeg และ whisper.cpp
- Portable ZIP เปิด native picker และถอดเสียงได้บน clean Windows ที่ไม่มี Python, FFmpeg หรือ whisper.cpp ติดตั้งอยู่
- รัน `py_compile` และ `scratch.test_app_unit` ผ่านก่อนส่งมอบ

## การตัดสินใจที่ต้องยืนยันก่อนเริ่มพัฒนา

แผนนี้ถือว่า Portable EXE เป็นเป้าหมายหลัก และจะจำกัด transcription ในโหมด Portable ให้ทำครั้งละหนึ่งงาน ส่วน Docker/server ยังคงใช้ upload แบบเดิม หากต้องการให้ server รับไฟล์ระดับหลาย GB ในอนาคต ควรวางระบบ storage และ reverse proxy แยกเป็นงานถัดไป
